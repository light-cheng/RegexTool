# 工业条码全场景优化与规则引擎增强（Industrial Barcode Optimization & Engine Enhancement）

Status: ready-for-agent

## Problem Statement

在复杂的离散制造（汽车零部件、航空航天、半导体电子、医疗器械）与智慧物流场景中，条码解码工程师需要为视觉读码器和上位机系统配置大量条码验证与字段捕获规则。现有的规则推断工具在“简单分隔符与定长字母数字”场景下表现良好，但在面对真实工业复杂条码时暴露出一系列核心痛点：

1. **变长流水号与序列号归纳脆弱（假性锚点过拟合）**：当条码字段长度动态变化（如流水号从 4 位到 9 位不等）或样本量较小时，模式推断引擎容易将样本中偶合相同的字符（如某些样本某位恰好都是数字 `5`）误判为硬编码固定文本，从而生成类似 `^\d{4}5\d{0,5}$` 这种畸形、脆弱且极易误杀合法条码的拼接正则。
2. **工业传输外壳与不可见控制字符处理欠缺**：高端工业条码（汽车 VDA 4994 GTL、北美 AIAG B-14、航空 ATA Spec 2000、军工 MIL-STD-130 UID）广泛采用 **ISO/IEC 15434** 封装外壳，包含不可见 ASCII 控制字符（ASCII 29 `<GS>` / `\x1D`、ASCII 30 `<RS>` / `\x1E`、ASCII 04 `<EOT>` / `\x04`）。工程师在复制粘贴或扫码枪输入时，这些控制字符极易丢失、损坏，或者工程师贴入的是 `<GS>` / `\x1D` 等可视化转义文本，工具缺乏对工业控制符的原生感知与高亮转义支持。
3. **扫码设备 AIM ID 前缀干扰**：工业固定式与手持扫码枪开启码制识别时，解码数据最前端会输出 3 字节 **ISO/IEC 15424 AIM ID**（如 `]d1`, `]d6`, `]C1`, `]Q1` 等）。工具若将其当做普通业务字符，会导致分段错乱并产生与实际业务系统不匹配的正则。
4. **工业数据标识符（DI）与 GS1 应用标识符（AI）字典覆盖有限**：汽车与半导体制造中存在大量标准 DI（如 VDA GTL 的 `1J`/`3J` 包装牌、`17V` CAGE 机构码、`6D`/`11D` 制造日期、`30P`/`30Q` 辅助料号数量等）以及医疗 UDI 体系中的常用 GS1 AI（`(01)` GTIN, `(10)` 批号, `(17)` 有效期, `(21)` 序列号）。现有工具未能充分利用这些工业字典实现智能命名与语义约束。
5. **校验位与业务层边界混淆**：对于 EAN-13、UPC-A、ITF-14、Code 39 Modulo 43 等带加权模运算校验位的条码，用户常期望正则能直接拦截校验错误。由于形式语言中 3 型正则文法天然无法进行算术求和取模，工具缺乏“标准码制识别 + 业务层校验提示 + 格式层精准收敛”的引导机制，容易让工程师对工具能力边界产生误解。

## Solution

在现有的便携单文件 Windows 离线 C++ 架构（ADR-0001）下，对核心规则推断引擎与输入验证系统进行工业级深度优化：

1. **智能变长归纳与抗过拟合对齐引擎（Anti-Overfitting & Variable-Length Synthesis）**：
   - 引入字符集同质性分析与动态规划序列对齐算法。当正例中某个字段出现长度浮动时，算法识别其整体字符特征（如 `\d` 或 `[A-Z0-9]`）并收敛为弹性区间 `{min,max}`，禁止在同质连续数据中切出偶然重复的单字符硬编码字面量，根治“假性锚点”缺陷。
2. **ISO/IEC 15434 协议外壳与不可见控制字符全生命周期支持**：
   - 原生支持扫描枪原始码流中的不可见控制字符（ASCII 29 GS, ASCII 30 RS, ASCII 04 EOT），并在 UI 上呈现醒目的文字徽标（如 `[GS]`, `[RS]`, `[EOT]`）。
   - 支持工程师直接粘贴可视化转义文本（如 `[)>06<GS>1P...` 或 `\x1D` 形式），工具自动完成物理控制字符与转义字符的双向解析，生成符合标准 C++ `\x1D` / `\x1E` 转义的合规正则。
   - 自动识别 ISO 15434 Format 05/06/12 标准头尾，生成精准的外壳正则。
3. **ISO/IEC 15424 AIM ID 智能探测与双模式候选生成**：
   - 自动探测 `]d1`, `]d2`, `]d6`, `]C0`, `]C1`, `]Q1`, `]A0`, `]I1` 等 3 字节码制前缀。
   - 生成候选时，提供“标准业务载荷正则（剥离 AIM ID 前缀）”与“全链路通信正则（包含 AIM ID 路由前缀）”两种变体，供工程师根据上位机架构灵活选用。
4. **全量工业 DI (ASC MH10.8.2) 与 GS1 AI 字典自动探测库**：
   - 内置汽车（VDA 4994 / AIAG B-10）、航天军工（ATA 2000 / MIL-STD-130）、医疗（UDI）标准 DI/AI 字典，自动匹配并赋予字段清晰的工业业务名称（如 `SingleContainerID`, `CAGE`, `GTIN`, `Batch`）。
5. **标准码制识别与业务校验解耦引导提示（Format Recognition & Checksum Advisory）**：
   - 当正例输入完全符合 EAN-13、UPC-A、EAN-8、ITF-14 等定长数字码制时，工具生成最严谨的格式正则（如 `^\d{13}$`），同时在验证面板与告警区明确提示：“检测到标准 EAN-13 条码，正则已完成格式与位数收敛；末位加权 Modulo 10 校验位须在业务代码中另行验算”。
6. **候选正则多样性与场景标签分类**：
   - 候选正则附带明确的工业场景分类标签：`[精准定长 (Strict)]`、`[弹性变长 (Elastic)]`、`[工业 DI 结构 (Industrial DI)]`、`[ISO 15434 外壳 (Structured Envelope)]` 等，按清晰层级排序供工程师选用。

3. 作为配置条码解码的工程师，我希望当正例包含不同长度的字母数字混合序列号时，工具能自动归纳为 `[A-Z0-9]{min,max}`，以便适配不同批次的序列号规则。

## Implementation Decisions

### 1. 架构与边界（保持 ADR-0001 约束）
- **形态**：纯 C++ 单文件 Windows 离线可执行程序，零网络、零外部动态依赖、零大模型运行时。
- **单一核心接缝**：所有规则归纳、分段推断、控制符解析、候选生成与多例验证均在核心引擎接口 `regex_tool::generate(const Project&)` 与 `regex_tool::verify_example(...)` 完成。UI 为纯无状态表现层。

### 2. 变长归纳与抗过拟合算法设计
- **字符同质性检测（Homogeneity Check）**：对分段内的所有样本字符进行类别统计（全数字 `\d`、全大写字母 `[A-Z]`、全字母数字 `[A-Z0-9]`）。
- **动态规划序列对齐与变长收敛**：
  - 当一组正例的分段长度不一致，但整个区间内的字符集高度同质时，引擎**禁止在中间切出单字符字面量**，直接归纳为单一字段 `\d{min,max}` 或 `[A-Z0-9]{min,max}`。
  - 只有当某个子串在所有正例中的出现位置、字符内容完全一致，且两侧存在明显的字符集跃迁（如字母到数字的跃迁）或明确的定界符时，才将其认定为固定字面量/标签。

### 3. ISO/IEC 15434 与控制字符全生命周期抽象
- **标准化控制 Token**：
  - 在引擎内部统一将原始字节 `0x1D`、转义字面量 `\x1D` 以及用户可视文本 `<GS>`、`[GS]` 归一化为抽象的 `Token::GS`。
  - 同样将 `0x1E` / `\x1E` / `<RS>` 归一化为 `Token::RS`，`0x04` / `\x04` / `<EOT>` 归一化为 `Token::EOT`。
- **正则表达式生成格式**：
  - 生成标准 C++ / PCRE 兼容的 16 进制转义序列（`\x1D`、`\x1E`、`\x04`）。
  - ISO 15434 报头生成为 `^\[\)>(\x1E|\x1D)?06\x1D` 或根据正例严格生成 `^\[\)>\x1E06\x1D`。

### 4. ISO/IEC 15424 AIM ID 探测与双变体生成
- 引擎内置标准 AIM ID 前缀识别器（`^\][a-zA-Z0-9][0-9a-zA-Z]`）。
- 若检测到正例均携带相同 AIM ID（如 `]d1` 或 `]d6`）：
  - 变体 A（推荐）：剥离 AIM ID，生成纯净的载荷数据正则 `^...$`，字段从实际载荷开始计数。
  - 变体 B（全链路）：保留 AIM ID，生成 `^\]d1...$`，首段固定为 AIM 标识符。

### 5. 扩展工业标准 DI / AI 字典
- **ASC MH10.8.2 DI 扩展表**：
  - 覆盖：`P`, `1P`, `2P`, `3P`, `30P`, `Q`, `30Q`, `S`, `1S`, `1T`, `T`, `V`, `17V`, `1V`, `K`, `14K`, `4K`, `D`, `6D`, `10D`, `11D`, `12D`, `1J`, `3J`, `4J`, `5J`, `6J`, `3S`, `4S`, `B`, `L`, `E`, `1N`, `Z`。
- **GS1 AI 扩展表**：
  - 覆盖：`00`, `01`, `02`, `10`, `11`, `13`, `15`, `17`, `21`, `240`, `310x`, `37`, `400`, `410`, `8004`。
- **紧凑拼接与分段推断**：
  - 利用字典前缀构建 Aho-Corasick 或前缀树（Trie），在没有分隔符的情况下优先按最长匹配 DI/AI 语义进行贪心候选切分。

### 6. 码制识别与业务校验提示（Advisory Messages）
- 引擎在生成阶段执行轻量级静态分析：
  - 若样本全为 13 位纯数字，打标 `Symbology::EAN_13` 并生成提示：“检测到 EAN-13 格式（纯数字 13 位），末位校验位计算公式：$C = (10 - (\sum \text{奇数位} + 3 \times \sum \text{偶数位}) \pmod{10}) \pmod{10}$，建议在业务层验算”。
  - 若样本全为 12 位纯数字，打标 `Symbology::UPC_A`。
  - 若样本符合 Code 39 字符集且包含校验位特征，给出 Modulo 43 校验建议。
- 若反例与正例在字符集和长度上完全一致（仅数值差异，如仅校验位错误），引擎在输出中给出特定的 `DiagnosticWarning`，明确提示工程师“反例为业务级错误样本，正则已成功收敛格式”。

## Testing Decisions

- **测试原则**：只测试核心引擎的公开接口（`regex_tool::generate` 与 `regex_tool::verify_example`），不测试任何内部实现细节；断言完全建立在真实工业标准条码样本与预期正则表达式上。
- **测试套件覆盖核心场景**：
  1. **变长流水号抗过拟合测试**：
     - 输入一组长度不等的纯数字正例（`1001`, `10002`, `100003`, `1000004`），断言推荐正则为 `^\d{4,7}$`，严禁出现中间带固定字符的畸形拼接。
  2. **ISO/IEC 15434 真实汽车 GTL / 航材条码测试**：
     - 输入包含 `[)>\x1E06\x1D1PA10402\x1DQ1000\x1DS00891\x1E\x04` 的正例，断言能精准识别 `<RS>` 和 `<GS>` 分隔符，生成合法转义正则，并正确捕获各字段值。
  3. **可视化转义输入兼容测试**：
     - 输入带有字面量 `<GS>` 或 `\x1D` 文本的条码，断言引擎能正确解析并生成匹配真实二进制字节的正则表达式。
  4. **AIM ID 智能分离测试**：
     - 输入带 `]d1` 或 `]d6` 的 Data Matrix 样本，断言能同时输出剥离 AIM ID 与保留 AIM ID 的候选变体。
  5. **连续紧凑工业 DI 拼接测试**：
     - 输入 `1PA10402Q10001TLOT2026S00891`，断言无需用户手动配置长度，引擎即可自动依据 DI 字典拆分出 `1P`, `Q`, `1T`, `S` 字段。
  6. **EAN-13 / UPC-A 格式收敛与校验提示测试**：
     - 输入真实 EAN-13 商品条码，断言产出 `^\d{13}$` 并生成针对 Modulo 10 校验位的业务层提示信息。
  7. **反例排除与精确定位测试**：
     - 测试结构错误反例（整串拦截）、字段字符集错误反例（精准指向出错段）、控制符缺失反例（指向对应分隔符段）。
